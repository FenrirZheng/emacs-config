# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Personal Emacs 30.1 config. Tracked: hand-authored Elisp ([`init.el`](init.el), [`early-init.el`](early-init.el), [`custom.el`](custom.el), [`lisp/`](lisp/)), bootstrap scripts ([`shell/`](shell/)), the GNU Global tag config ([`gtags.conf`](gtags.conf) — extended-skip copy of the system one, see the [GTAGS index hygiene note](#conventions--gotchas-worth-knowing-before-editing)), the [pre-commit hook](.githooks/pre-commit), and docs (`CLAUDE.md` itself, [`README.md`](README.md), [`FEATURES.md`](FEATURES.md), [`_doc/GO.md`](_doc/GO.md), [`_doc/JAVA.md`](_doc/JAVA.md)). Everything reproducible or stateful is gitignored — `elpa/`, `eln-cache/`, the no-littering `var/` + `etc/`, the vendored `eca/` binary, and `tree-sitter/` grammars.

The companion to this file is [`FEATURES.md`](FEATURES.md) (the "what keys do I press" cheat sheet) — keep them in sync when bindings or workflow change.

## Architecture: thin loader + per-area modules

[`init.el`](init.el) is intentionally tiny. It bootstraps the package system (MELPA + GNU ELPA, `use-package-always-ensure t`, `no-littering`, `exec-path-from-shell`), pushes `lisp/` and `lisp/languages/` onto `load-path`, then `mapc #'require`s a fixed list of `init-<area>` modules in the order shown in the file's header comment. **That load order is load-bearing**: cross-section `use-package :after` wiring in the modules (e.g. `consult-eglot :after (consult eglot)`, `magit-delta :after magit`) assumes earlier modules have already declared their packages. Do not reshuffle without verifying the `:after` edges.

The top-level `init-<area>` modules under [`lisp/`](lisp/) (`init-defaults`, `init-system-packages`, `init-completion`, `init-corfu`, `init-snippets`, `init-editing`, `init-languages`, `init-git`, `init-terminal`, `init-appearance`, `init-dired`, `init-org`, `init-org-roam`, `init-ai`, `init-aidermacs`, `init-tmux-claude`, `init-alacritty-claude`) mostly correspond to one section of the pre-2026-05-19 monolithic `init.el` (see `git log --oneline` for the split commits); `init-aidermacs`, `init-tmux-claude`, and `init-alacritty-claude` are later standalone additions. Section numbers in module headers refer to that pre-split layout — they're history, not a current TOC; read the module names instead.

**Per-language modules live under [`lisp/languages/`](lisp/languages/)** — `init-java`, `init-go`, `init-python`, `init-rust`, `init-typescript`, `init-c-cpp`, `init-lua`, `init-vue`, `init-web`, `init-markdown`. These were split out of the former monolithic `init-languages.el` so each language is easy to find and edit in isolation. [`lisp/init-languages.el`](lisp/init-languages.el) now holds only the **language-agnostic** infrastructure (project.el, envrc, the Eglot core block, eglot-booster, consult-eglot, xref, breadcrumb, eldoc routing, ggtags + combobulate package declarations, treesit-auto, flymake, sideline, apheleia, dape) and **must load before** the per-language modules — each of those attaches its own `eglot-ensure` hook (via `add-hook`), registers its server's `eglot-workspace-configuration` entry (via `(with-eval-after-load 'eglot (setf (alist-get :SERVER …) …))`), and adds its `combobulate-mode` / `ggtags-mode` hooks onto the shared package declarations in the core. So "where is language X configured" → [`lisp/languages/init-X.el`](lisp/languages/); "where is the shared Eglot / tree-sitter / debugger setup" → [`lisp/init-languages.el`](lisp/init-languages.el).

Local Elisp (not on MELPA): [`lisp/claude-jobs-view.el`](lisp/claude-jobs-view.el) — a `tabulated-list-mode` UI over the external `jobctl` CLI for persistent Claude Code sessions. Entry point `M-x claude-jobs-view`. Loaded lazily via `:commands` autoload in [`lisp/init-ai.el`](lisp/init-ai.el).

## Startup discipline (`early-init.el`)

[`early-init.el`](early-init.el) runs BEFORE the package system and the first frame. It owns:
- GC tuning (`gc-cons-threshold` raised to `most-positive-fixnum` for startup, restored to 32 MB on `emacs-startup-hook`).
- `file-name-handler-alist` suspension during init (every `require` walks it — emptying it saves measurable time).
- Frame chrome via `default-frame-alist` (menu/tool/scroll bars off **before** the first frame paints — calling `menu-bar-mode -1` in `init.el` is too late and causes a flash).
- `package-enable-at-startup nil` so the implicit pre-init `package-activate-all` doesn't duplicate `init.el`'s explicit `(package-initialize)`.

Don't move any of those into `init.el` — the cost has already been paid by the time it runs.

## Package-install discipline (load-bearing quirks)

- **The archive is NEVER refreshed at startup** (network-free boot). After adding a new `use-package` block whose package isn't already in `elpa/`, run `M-x my/package-refresh` then restart Emacs — otherwise the install fails to find the package.
- **`use-package-always-ensure` is `t`** — plain `(use-package foo …)` auto-installs `foo` from MELPA. **Built-ins must say `:ensure nil`** (e.g. `project`, `flymake`, `ibuffer`, `recentf`, `savehist`, `saveplace`, `winner`, `which-key`, `org`, `vertico-directory`, `corfu-popupinfo`, `dired`). If you forget, MELPA pulls a redundant copy that may shadow the built-in. **`eglot` is the deliberate exception** — it's `:ensure t` (upgraded off the bundled copy, see the next bullet).
- **Eglot is upgraded to the GNU ELPA release** (not the copy bundled with Emacs 30.1) — needed for native call / type hierarchy (`eglot-show-call-hierarchy` / `eglot-show-type-hierarchy`, on `C-c h c` / `C-c h t`), which only exists in Eglot ≥1.19 (2025-10). Two load-bearing quirks: **(1)** `:ensure t` alone can't upgrade a built-in — use-package's ensure short-circuits on `package-installed-p` (always `t` for a bundled package) and never calls `package-install`. The repo therefore sets `package-install-upgrade-built-in t` in [`init.el`](init.el) so a manual `M-x package-install RET eglot` actually replaces the built-in; **(2)** since `elpa/` is gitignored, a **fresh clone falls back to the bundled Eglot** until you run that one-time install (see the [fresh-clone bootstrap](#fresh-clone-bootstrap)). Side effect: installing Eglot 1.23 also pulls `flymake` 1.4.5 into `elpa/` as a dependency, which then shadows the built-in `flymake` even though its own `use-package` block still says `:ensure nil` — benign (the block just configures the newer copy). eglot-booster's `eglot--connect` / `jsonrpc--json-read` advice was verified to still apply against 1.23.
- **GitHub-only packages use `use-package`'s `:vc` keyword** (Emacs 30 native `package-vc-install`, no straight.el / quelpa needed) — see `eglot-booster` and `combobulate` in [`lisp/init-languages.el`](lisp/init-languages.el). The pinned URLs are recorded in [`custom.el`](custom.el) under `package-vc-selected-packages` so a fresh clone reproduces the same fetch. Update later via `M-x package-vc-upgrade RET <name> RET`.
- **`M-x customize` writes to [`custom.el`](custom.el)** (`custom-file` is set in [`lisp/init-defaults.el`](lisp/init-defaults.el), which also `(load custom-file)`). There is intentionally **no** `custom-set-variables` block in `init.el` — keeping a duplicate would let "whichever loads last" silently win.
- **`no-littering` is loaded eagerly (`:demand t`)** in `init.el` BEFORE the modules require packages that drop state files. The repo's `.gitignore` whitelists `/var/` and `/etc/` in one line each, replacing per-file ignores.

## Build / test / run

This is plain Elisp — there is no compile or test command. Workflow:

- **Reload after editing**: `M-x load-file RET init.el RET`, or just restart Emacs. Modules can be reloaded individually via `M-x load-file RET lisp/init-<area>.el RET` once their `(require 'init-<area>)` has already run once (otherwise `provide` hasn't registered).
- **Stale `.elc` artefacts**: byte-compiled `*.elc` files sit next to their `.el` siblings in [`lisp/`](lisp/) and are gitignored. `load-prefer-newer t` (set in `early-init.el`) means a fresh `.el` wins, but if you suspect a stale `.elc` is being preferred, delete it: `fdfind -e elc -X rm` from this directory.
- **Tree-sitter grammars** live in [`tree-sitter/`](tree-sitter/) (gitignored, regenerated by `treesit-install-language-grammar`). `treesit-extra-load-path` in `init-languages.el` adds that dir so next startup finds them. Emacs 30.1 caps the grammar ABI at 14 (`treesit-library-abi-version` ⇒ 14), and several upstream grammars have moved to ABI 15 — handled two ways: **(a) exclude + fall back** for `css` / `json` (dropped from `treesit-auto-langs`, use built-in `css-mode` / `js-json-mode`); **(b) pin to the newest ABI-14 tag + rebuild** for `c` (v0.23.6), `lua` (v0.3.0), and `rust` (v0.23.3) — these stay in `treesit-auto-langs`, each language module sets the grammar's `abi14-revision` recipe slot, and a standalone Makefile deployer lives under [`rust/treesit-grammar*/`](rust/) (see the [rust workspace](#rust-workspace-rust) note). Pin (b) is preferred whenever an ABI-14 tag exists; `lua` was an (a)-style exclusion until 2026-06-08, when `v0.3.0` was found to be a valid ABI-14 tag and it moved to (b) (`lua-ts-mode`, with `lua-mode` kept as the no-grammar fallback).

## C++ dynamic modules (`cpp/`)

[`cpp/`](cpp/) is a **workspace for native Emacs dynamic modules** (C++ wrapping the `emacs-module.h` ABI). It is a multi-project CMake tree, NOT a git submodule: the top-level [`cpp/CMakeLists.txt`](cpp/CMakeLists.txt) is an aggregator (`add_subdirectory(<name>)` per module) and every module's `.so` is emitted into `cpp/lib/`. Build everything with [`cpp/build.sh`](cpp/build.sh) (or `cpp/build.sh clean`); both `cpp/build/` and `cpp/lib/` are gitignored (per-module `src/`, `vendor/`, `CMakeLists.txt` stay tracked). To add a module: create `cpp/<name>/CMakeLists.txt` with an `add_library(<name> MODULE …)` target (`PREFIX ""`, `SUFFIX ".so"`), put sources under `cpp/<name>/src/`, add one `add_subdirectory(<name>)` line, and load from elisp via `(module-load (expand-file-name "cpp/lib/<name>.so" user-emacs-directory))`. Workspace overview + per-module docs: [`cpp/README.md`](cpp/README.md).

Current modules:

- **`junit-core`** ([`cpp/junit-core/`](cpp/junit-core/)) — JUnit test discovery for Java. Uses the tree-sitter C API (system `libtree-sitter` runtime via `apt install libtree-sitter-dev`, plus the **vendored** java grammar at [`cpp/junit-core/vendor/tree-sitter-java/`](cpp/junit-core/vendor/tree-sitter-java/) — `parser.c` + its `tree_sitter/` headers, `LANGUAGE_VERSION 14`, compiled in; the runtime is the *only* apt dep) to find the `@Test`-family method at a line (JUnit 4 + 5, nested `@Nested` → `Outer$Nested`), detect Maven vs Gradle by walking up the tree, and build the exact `mvn`/`gradle` command. It deliberately **stops at command construction — it never launches a process**. The elisp front-end [`lisp/junit-runner.el`](lisp/junit-runner.el) loads the `.so` on demand (`junit-runner-module` → `cpp/lib/junit-core.so`) and runs the command via `compile`. Keys are wired in [`init-java.el`](lisp/languages/init-java.el) under the **`C-c t`** prefix (`t` dwim / `m` method / `f` file / `b` build) — mirrors Go's `C-c t t`/`C-c t d` and, like Go, makes `C-c t` a test prefix that **shadows vterm inside Java buffers only**. Module API + detection rules: [`cpp/junit-core/README.md`](cpp/junit-core/README.md).

## Rust workspace (`rust/`)

[`rust/`](rust/) is the Rust analogue of [`cpp/`](cpp/README.md): a multi-project workspace for Rust that supports this Emacs config, aggregated by a thin **Make** fan-out ([`rust/Makefile`](rust/Makefile) forwards `all`/`install`/`verify`/`clean`/`distclean` to each `SUBPROJECTS` entry — the Make analogue of cpp's `add_subdirectory`). NOT a git submodule; only code that exists *for the config* belongs here (unrelated Rust apps stay as untracked `~/code/` clones). The name is mostly historical: alongside actual Rust crates it also hosts the **tree-sitter grammar deployers**, which are `cc` builds of C grammar sources (`parser.c`/`scanner.c`), not Rust — they live here as a pragmatic exception because the original `treesit-grammar` started here and the Make fan-out is a clean home for them. To add a subproject: create `rust/<name>/` with a Makefile exposing those five phony targets, add `<name>` to `SUBPROJECTS`, and add a `/rust/<name>/...` block to [`.gitignore`](.gitignore) for its build artefacts. Workspace overview: [`rust/README.md`](rust/README.md).

Current subprojects:

- **`treesit-grammar`** / **`treesit-grammar-c`** / **`treesit-grammar-lua`** ([`rust/treesit-grammar/`](rust/treesit-grammar/), [`-c/`](rust/treesit-grammar-c/), [`-lua/`](rust/treesit-grammar-lua/)) — NOT Emacs modules; hand-rolled `cc` builds that clone tree-sitter-{rust,c,lua} at the **newest ABI-14 tag** (rust `v0.23.3`, c `v0.23.6`, lua `v0.3.0` — Emacs 30.1 caps the grammar ABI at 14; the upstreams' newer tags are ABI 15 and load as `version-mismatch: 15`) and deploy `libtree-sitter-{rust,c,lua}.so` into [`tree-sitter/`](tree-sitter/). Each has a matching `abi14-revision` recipe pin in its language module ([`init-rust.el`](lisp/languages/init-rust.el) / [`init-c-cpp.el`](lisp/languages/init-c-cpp.el) / [`init-lua.el`](lisp/languages/init-lua.el)) so `treesit-auto` auto-install fetches the same ABI-14 tag — **keep each Makefile's `GRAMMAR_TAG` in sync with its module's `abi14-revision`**. The three Makefiles are near-identical (the build auto-detects whether the grammar ships a `scanner.c`: rust/lua do, c is parser-only). See each subproject's README + the [Build/test/run](#build--test--run) tree-sitter note.
- **`question-queue-core`** ([`rust/question-queue-core/`](rust/question-queue-core/)) — an **Emacs dynamic module** (cargo `cdylib`) over the **raw emacs-module ABI**, bound via **bindgen** (`build.rs` runs bindgen over [`wrapper.h`](rust/question-queue-core/wrapper.h) → the system `/usr/include/emacs-module.h`; the hand-written unsafe marshalling lives in [`src/emacs.rs`](rust/question-queue-core/src/emacs.rs), which `transmute`s the env fn-pointers to ABI-stable local types so it doesn't depend on bindgen's `ptrdiff_t` spelling). Like junit-core it is **pure compute + local file I/O — never launches a process or watches a directory**. It exposes `qq-core-submit` (assemble a region+question markdown doc, generate a unique name, **atomic** temp-+-rename write into a queue's `input/` dir) and `qq-core-version`; it also still exports `qq-core-parse-answer`, but the front-end no longer calls it — answers are now opened straight from the `output/` file rather than parsed (the function is retained, harmless, and unit-tested). Built by `make -C rust/question-queue-core` into `rust/lib/question-queue-core.so` (workspace-wide `rust/lib/`, the analogue of `cpp/lib/`; bare name, no `lib` prefix, for `module-load`). Front-end + keybinding below. Module API: [`rust/question-queue-core/README.md`](rust/question-queue-core/README.md).

The matching elisp front-end is [`lisp/question-queue.el`](lisp/question-queue.el) (lazy-wired in [`lisp/init-ai.el`](lisp/init-ai.el) via `:commands`/`:bind`, like `claude-jobs-view`): `M-x question-queue-ask` (**`C-c q q`**) ships a typed question — optionally with the highlighted region as code context (no region = question-only; the Rust side omits the `# Context` block when the region is empty) — through `qq-core-submit` into the queue's `input/`, watches `output/` with **`file-notify`** (inotify), and when the matching answer file lands simply opens that `output/<name>` file directly in a buffer (bottom side window) — the source buffer is never modified. Build once with `M-x question-queue-build` (a fresh clone falls back to a helpful error until then, exactly like junit-runner). The native↔elisp split mirrors junit-core: compute/atomic-I/O in Rust, region-capture/watch/display in elisp. **Queue directory**: there is **no built-in default** — `question-queue-dir` defaults to nil, so the user must supply a root. The normal path is the interactive prompt on the first `C-c q q` of a session (remembered thereafter); it can also be set persistently by customizing `question-queue-dir`, or changed any time with `question-queue-set-dir` (**`C-c q d`**) / `C-u C-c q q`. If none is set, `question-queue-ask` errors via `question-queue--root` rather than falling back to a baked-in path. `file-notify` watches are keyed per `output/` directory, so changing the root while an earlier request is still pending keeps that request resolving to its original queue (the per-request `:input-dir`/`:output-dir` are stamped at submit time).

## Fresh-clone bootstrap

```bash
git clone <remote> ~/.emacs.d
git -C ~/.emacs.d config core.hooksPath .githooks   # wire pre-commit (local config, not tracked)
~/.emacs.d/shell/install.sh                         # apt + npm/cargo/go/rustup deps
emacs                                               # first launch: use-package installs missing packages
```

[`shell/install.sh`](shell/install.sh) is a thin orchestrator over two halves: [`install-root.sh`](shell/install-root.sh) (apt packages; self-elevates via `sudo`) and [`install-user.sh`](shell/install-user.sh) (cargo / go / rustup / npm / terminfo; refuses to run as root so toolchain caches don't land under `/root/`). Shared helpers live in [`install-lib.sh`](shell/install-lib.sh). `install-user.sh` flips npm's global prefix to `$HOME/.npm-global` so `npm install -g` no longer needs sudo — add `$HOME/.npm-global/bin` to `PATH` once for the new prefix to be useful.

After first launch, also:
- `M-x nerd-icons-install-fonts` once (modeline glyphs).
- `M-x org-roam-db-sync` once (first roam DB build, `~/code/org-roam/`).
- `M-x my/package-refresh` then `M-x package-install RET eglot RET` once, then restart — upgrades Eglot off the bundled 30.1 copy to the GNU ELPA release (≥1.19) for native call / type hierarchy. The first launch can't do this automatically (`:ensure t` won't upgrade a built-in); `package-install-upgrade-built-in t` is already set in [`init.el`](init.el) so the manual install replaces the bundled copy. See [Eglot is upgraded to the GNU ELPA release](#package-install-discipline-load-bearing-quirks).
- *(optional, only for Java JUnit-at-point)* `sudo apt install libtree-sitter-dev` then `~/.emacs.d/cpp/build.sh` (or `M-x junit-runner-build`) — builds the `junit-core` C++ module into `cpp/lib/`. Skippable: [`junit-runner.el`](lisp/junit-runner.el) degrades to a build hint until then. See [C++ dynamic modules (`cpp/`)](#c-dynamic-modules-cpp).

## Pre-commit hook

[`.githooks/pre-commit`](.githooks/pre-commit) runs `gitleaks git --staged`. `core.hooksPath` is local config, so re-run `git config core.hooksPath .githooks` after any fresh clone. If `gitleaks` isn't on `PATH`, the hook prints a warning and no-ops — install from the upstream releases.

If the hook blocks a commit, fix the underlying secret; do not reach for `--no-verify` (per global rule).

## Conventions & gotchas worth knowing before editing

- **`$HOME` is itself a git repo** (the dotfiles tree). [`lisp/init-languages.el`](lisp/init-languages.el) advises `project-try-vc` to ignore `$HOME` as a project root, and adds `.project`, `Cargo.toml`, `go.mod`, `pyproject.toml`, `CLAUDE.md`, `package.json`, `Makefile` to `project-vc-extra-root-markers`. Drop an empty `.project` file in any directory you want treated as a project. If project root detection seems stuck on a stale answer after editing the markers list, run `M-x fenrir/project-reset-cache` — `project-try-vc` memoises via `vc-file-setprop` and the function clears the `vc-file-prop-obarray`.
- **`$HOME` is also a Magit hazard**: with ~1500 tracked files plus `status.showUntrackedFiles=no` hiding ~1M items, the untracked-files section and `diff-hl-dired-mode` were dropped from this config — see [`lisp/init-git.el`](lisp/init-git.el).
- **Vertico, not Corfu, drives in-buffer completion**: `completion-in-region-function` is bound to `consult-completion-in-region` in [`lisp/init-completion.el`](lisp/init-completion.el)'s `:init`. `global-corfu-mode` is **not** enabled — Corfu stays installed (`:defer t`) so flipping back is a one-line edit. Don't enable `global-corfu-mode` casually; it sets its own buffer-local `completion-in-region-function` and silently overrides the consult routing.
- **`C-x b` is `ibuffer`, not `switch-to-buffer`** — the consult fuzzy switcher lives on `C-x B` (shift). Reason: tmux's default `C-b` prefix swallows the second keystroke in a TTY frame, ruling out the default `C-x C-b`.
- **`eglot-booster` monkey-patches `eglot--connect`** (`:filter-args` advice `eglot-booster--wrap-contact`, plus an `:around` on `jsonrpc--json-read`). An Emacs **or Eglot** upgrade may break it; recover at runtime with `M-x eglot-booster-mode` (toggles off). Verified intact against the ELPA Eglot 1.23 bump (the call/type-hierarchy upgrade above) — both advices still attach.
- **Eglot IDE keybindings live in the core `:bind (:map eglot-mode-map …)`** in [`lisp/init-languages.el`](lisp/init-languages.el): `C-c .` code actions, `C-c r` rename, `C-c i` organize-imports, `C-c x` extract, `C-c f` `eglot-format`, `C-c h c`/`h t` call/type hierarchy, `C-c h i` toggle inlay hints, `C-c h s` toggle semantic tokens (full prose in [FEATURES.md §7](FEATURES.md)). Two regression traps for future editors: **(1)** these refactor keys are deliberately NOT under the `C-c o` prefix — that belongs to combobulate (`combobulate-key-prefix`, `C-c o n` = combobulate-rename) and would collide in buffers where both minor modes are live. **(2)** `C-c f` (`eglot-format`) is **manual only** — apheleia owns format-on-save; never add `eglot-format`/`eglot-format-buffer` to `before-save-hook` or it double-formats against apheleia and reintroduces a save-time cursor jump. **(3)** `eglot-semantic-tokens-mode` (`C-c h s`) is intentionally a per-buffer toggle, **not** a global hook — it can fight tree-sitter font-lock and its extra faces collapse on an 8/16-colour TTY; don't "helpfully" globalize it. Inlay hints, by contrast, ARE global-on (`eglot-managed-mode` → `eglot-inlay-hints-mode`); Java pushes `java.inlayHints.parameterNames=all` and C/C++ registers clangd with `--inlay-hints` (belt-and-suspenders — clangd ≥14 defaults them on; per-hint-kind tuning lives in clangd's `~/.config/clangd/config.yaml`, not the launch flags).
- **`ggtags-mode` is hooked for C/C++, Python, Go, and JS/TS/TSX** (the per-language `add-hook` calls in [`lisp/languages/`](lisp/languages/)) so a buffer with a prebuilt `GTAGS` but no live server still navigates via `M-.` / `M-?` (the `~/code/coinsasia/GTAGS` case). **Load-bearing, easily-missed trap**: `ggtags-mode` is *not just* an xref backend — its `ggtags-mode-map` rebinds `M-.` → `ggtags-find-tag-dwim`, which shells out to `global` and **bypasses `xref-backend-functions` entirely**, so in any buffer where both Eglot and `ggtags-mode` are live it would shadow Eglot's `M-.`. [`lisp/init-languages.el`](lisp/init-languages.el) therefore *neutralizes* `M-.` and `C-M-.` in `ggtags-mode-map` (a `with-eval-after-load 'ggtags` `define-key … nil` right after the ggtags `use-package` block) so `M-.` stays the global `xref-find-definitions` and dispatches over `xref-backend-functions` — where Eglot prepends and wins when attached, and `ggtags--xref-backend` answers only as the no-server fallback. **Do not delete that `define-key … nil` block as "redundant"** — without it, gtags silently shadows gopls/tsserver/clangd on `M-.`. (M-? / M-, are left intact — this ggtags version never bound them.) This is the per-key version of the config's standing "never globalize `ggtags-mode`" rule.
- **GTAGS index hygiene — nested-shadow + junk-bloat, both fixed in [`lisp/init-languages.el`](lisp/init-languages.el)** (the gtags build machinery; `C-c g g` build/update, `C-c g d` diagnose). Two failure modes a multi-language monorepo (`~/code/coinsasia`) surfaced, each with a durable guard:
  - **Nested-index shadowing.** GNU Global resolves a lookup to the **nearest ancestor `GTAGS`** walking up from the file, so a `GTAGS` in a subdirectory silently hides the root index for every file beneath it (`backend/GTAGS` hid the top-level `GTAGS`; xref answered from the stale sub-index and the root looked "unread"). Guard: `fenrir/gtags--sweep-nested-indexes` runs on every (re)build (gated by `fenrir/gtags-sweep-nested`, default `t`) to delete nested indexes so the freshly-built root is the only resolvable one; **`C-c g d`** (`fenrir/gtags-diagnose-duplicates`) is the on-suspicion command — lists every `GTAGS` in the subtree (`[root]`/`[nested]`, size+mtime) and offers to remove the shadows. The update path also warns when the buffer's index is itself shadowed by a higher one (`fenrir/gtags--ancestor-index-root`).
  - **Dependency/build junk + re-bloat on update.** The build injects `GTAGSCONF` (`fenrir/gtags-conf`, default the **tracked** [`gtags.conf`](gtags.conf)) on **both** `gtags` create and `global -u` update. That file is a self-contained copy of `/etc/gtags/gtags.conf` whose `common:` skip list additionally drops `node_modules/ vendor/ venv/ .venv/ dist/ build/ target/ …` — the dirs the stock conf does **not** skip. Why it must be the config and not a `gtags -f` file list: **`global -u` re-traverses the whole filesystem** and re-adds anything not skipped (verified: coinsasia went 2.5 MB → 3.85 GB on a single bare `global -u`), so only a skip list reaches the update path. Owning the conf in-repo keeps the exclusion reproducible without editing the root-owned system file; the build falls back to `/etc/gtags/gtags.conf` if ours is absent. Refresh-from-upstream instructions live in [`gtags.conf`](gtags.conf)'s own header.
- **Java on Eglot + jdtls** (migrated from lsp-mode on the `try/java-on-eglot` branch; all Java code lives in [`lisp/languages/init-java.el`](lisp/languages/init-java.el)): `java-mode` / `java-ts-mode` hook `eglot-ensure` like every other language. The jdtls launcher (`fenrir/jdtls-launch-command` in [`lisp/languages/init-java.el`](lisp/languages/init-java.el)) reuses the historic bundle at [`var/lsp-java/eclipse.jdt.ls/server/`](var/lsp-java/eclipse.jdt.ls/) originally downloaded by lsp-java — ~150 MB, kept in place after the migration to avoid a re-download. Workspace metadata still lives at [`var/lsp-java/workspace/`](var/lsp-java/workspace/); delete that subdir out-of-band to force jdtls to re-import every project from scratch. JVM args + references-speed knobs mirror the lsp-java preset (`-Xmx3G`, `includeDecompiledSources :json-false`, `includeAccessors :json-false`, code-lens off) and are pushed via `eglot-workspace-configuration`'s `:java` entry. The launcher also appends `:initializationOptions` (built by `fenrir/jdtls--java-settings`) so the `:java` settings reach jdtls at the `initialize` request, not just the later `workspace/didChangeConfiguration` — load-bearing for anything the initial project scan reads (the Maven-userSettings and Gradle-disable notes in the next bullet). The `jdt://` URI scheme handler is the load-bearing piece for navigation — without it, `M-.` into a JDK / third-party-jar class silently fails because Eglot has no native handler; ours is registered in `file-name-handler-alist` and relays to jdtls' `java/classFileContents` extension (enabled via `extendedClientCapabilities.classFileContentsSupport` in those same initializationOptions).
- **Java project roots** (`fenrir/project-find-java-build-root`, prepended to `project-find-functions` ahead of `project-try-vc`): resolves a Java buffer's root in two tiers. **Tier 1 — container marker**: if an ancestor holds `.eglot-java-workspace` (filename in `fenrir/java-workspace-marker`), that ancestor is THE root for every Java file beneath it — fusing several independent Maven/Gradle reactors under one container (e.g. `~/code/hitok2/` holding `im-combined-hitok` + `im-combined-api` + `hitok-java-backend`) into ONE Eglot server → ONE jdtls Eclipse workspace, so cross-project find-references / navigation work and a sibling repo's buffer never spawns a second jdtls fighting over the shared `-data`. **Tier 2 — topmost-pom**: otherwise the highest consecutive ancestor with `pom.xml` / `build.gradle*` (the multi-module reactor root). `.project` markers are deliberately ignored here because Eclipse m2e regenerates them inside every module on import, and the deepest-wins `project-try-vc` would then pin jdtls to a too-deep sub-module (symptom: `M-?` only returns hits inside that sub-module). The return shape is `(list 'vc BACKEND ROOT)` with an `abbreviate-file-name`'d path so every sibling buffer keys to the SAME Eglot session (mismatched `~/...` vs `/home/...` or `vc` vs `vc-local` would split sessions). Two container gotchas: **(1)** Buildship ignores `java.import.exclusions`, so a non-Java subtree like a React Native app's `android/` Gradle build (e.g. `~/code/hitok2/im-pay/`) stalls jdtls init — `fenrir/jdtls--java-settings` therefore sets `import.gradle.enabled=false` whenever a container marker is in play (standalone Gradle projects, with no marker → own server, keep it on); **(2)** the same artifact checked out twice under one container (a standalone `im-combined-hitok` plus `im-combined-api/im-combined-hitok`) imports as duplicate JDT projects and double-counts references — keep one copy. Maven dep resolution: jdtls is pointed at [`~/.m2/settings-public.xml`](file:///home/fenrir/.m2/settings-public.xml) via `java.configuration.maven.userSettings` because the default `~/.m2/settings.xml` mirrors to an internal Nexus (`mosainet.com` / `192.168.130.170:8081`) that's unreachable off the corp net and makes import hang on TCP timeouts, blocking every LSP request; the public file shares the `~/.m2/repository` cache but skips the corp profile. Inspect live state with `M-x eglot-events-buffer` or by walking `eglot--servers-by-project` (a hash-table — `maphash`, not `cl-loop for ... in`). `M-x fenrir/eglot-java-add-roots-under RET <container> RET` remains for ad-hoc `workspace/didChangeWorkspaceFolders` additions, but the container marker is the durable mechanism. The booster (`emacs-lsp-booster` Rust binary) wraps the jdtls connection automatically — same generic `eglot--connect` advice that handles every other Eglot server, and it prepends to the PROGRAM part only so the launcher's trailing `:initializationOptions` survives.
- **DAP debugging is `dape`** — Eglot-aligned, ships with GNU ELPA, the `use-package` block at the end of [`lisp/init-languages.el`](lisp/init-languages.el). Breakpoints render in the buffer **margin** (`B` glyph), visible on TTY frames; lsp-mode's `dap-mode` (which drew them with GUI-only fringe bitmaps) was removed when Java migrated to Eglot. **Java debugging is unsupported** in this config until either dape grows a Java adapter or someone writes a manual bridge to `java-debug` — use IntelliJ / VSCode for real Java debugging until then. Debug-adapter binaries live outside the repo: only Go's `dlv` is on `PATH`; `debugpy` / `gdb` / `codelldb` / `vscode-js-debug` install per language as needed. Keybindings are catalogued in [FEATURES.md §7](FEATURES.md).
- **OSC 52 clipboard bridge** (TTY-only) is wired in [`lisp/init-defaults.el`](lisp/init-defaults.el) — `interprogram-cut-function` emits `\e]52;c;...\a` so cuts cross the tmux/SSH boundary to the host clipboard. Don't override `interprogram-cut-function` in another module.
- **Byte-compilation byproducts** (`init-<area>.elc`) are gitignored but persist locally; they're regenerated on demand. Timestamped backups (`init.el.bak-YYYYMMDD-HHMM`) from ad-hoc edits are also gitignored — clean them up periodically.
